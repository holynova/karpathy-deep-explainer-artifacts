分布式系统的终极命题：网络不可靠、时钟不可靠与状态共识

在分布式环境下，没有全局物理时钟，任何网络包都可能丢失、乱序或延迟数秒，硬件崩溃是系统常态。真正的架构师不追求“永不宕机”，而是通过严密的数学证明与工程契约，在非可靠底座上构建可靠的分布式状态机。

POINT 01

分布式共识协议与状态机复制 (Raft Consensus & Log Replication)

领导者选举 · 脑裂自愈
// ASD-STE100 架构规约：

1. Nodes exist in three states: Follower, Candidate, or Leader.

2. If Followers do not receive Leader heartbeats before the randomized election timeout, they become Candidates.

3. A Candidate needs votes from a strict majority (N/2 + 1) to become Leader.

4. The Leader commits log entries only after a majority of Followers write them to disk.

5. In network partitions, minority partitions cannot commit writes, preventing split-brain corruption.

POINT 02

一致性模型深度辨析：线性一致性、因果一致性与 PACELC 定理

一致性光谱 · 延迟权衡

许多人误将 CAP 当作设计圣经，但 CAP 存在致命缺陷：它只讨论“存在网络分区时”的极度对立情况，忽略了 99.9% 正常无分区时间的系统行为。

// PACELC 定理公式化表达：
如果存在分区 (Partition)：系统必须在可用性 (Availability) 与一致性 (Consistency) 之间抉择；
否则 (Else, 正常状态)：系统必须在延迟 (Latency) 与一致性 (Consistency) 之间抉择。
典型分类： MongoDB / Cassandra (PA/EL) 追求极低延迟； Spanner / CockroachDB (PC/EC) 不惜以跨机房往返延迟换取线性一致性。

分布式事务终局：Saga 编排器与 Transactional Outbox + CDC

最终一致性 · 可靠投递
// ASD-STE100 架构规约：

1. Two-Phase Commit (2PC) blocks resources and causes severe latency under high scale.

2. Sagas break transactions into local steps with corresponding compensating rollback actions.

3. Transactional Outbox writes the domain change and the outbound message into the same local database transaction.

4. Debezium CDC reads database transaction logs (e.g. MySQL Binlog) and streams events to Kafka with zero dual-write inconsistency.

POINT 04

现代存储引擎剖析：LSM-Tree vs B+ Tree、读写放大与分层压缩

追加写 · 写放大控制

关系型数据库与 NoSQL 的核心性能鸿沟来源于存储引擎结构：

B+ Tree (InnoDB / PostgreSQL)
  • • 读优化：随机点查性能极致，单次点查仅需 3~4 次磁盘寻道。
  • • 原地修改：每次写入需要修改磁盘物理页，引发严重的随机 I/O 与双写缓冲 (Doublewrite Buffer)。
  • • 写放大系数通常在 10 ~ 30 倍。
LSM-Tree (RocksDB / TiDB / Cassandra)
  • • 写优化：顺序追加写入 WAL 与内存跳表 (MemTable)，写入吞吐高出数量级。
  • • 后台分层压实 (Leveled Compaction)：内存满后刷盘为 SSTable，后台线程周期性合并有序文件。
  • • 布隆过滤器 (Bloom Filter)：快速跳过不包含目标 Key 的 SSTable，缓解读放大。
POINT 05

高性能缓存设计与双写一致性陷阱 (Cache-Aside & Delayed Double Delete)

击穿/穿透/雪崩 · Binlog 订阅

“先更新数据库，再删除缓存” 在并发极端场景仍可能出现脏读：读线程在更新前读取了旧 DB 数据，因卡顿延迟在删缓存之后将旧数据写回 Redis。

终极解法：基于 CDC Binlog 的异步淘汰 (Canal / Debezium)

应用层只负责修改数据库，不直接碰缓存；由独立消费组件监听 MySQL Binlog 增量，确认事务提交成功后，再向 Redis 发送删除指令，结合消息队列的重试保障，彻底切断应用层双写时序竞争。

POINT 07

分布式限流与流量整型算法 (Token Bucket vs Leaky Bucket vs Sliding Window)

突发平滑 · Redis Lua 原子计数

在高并发网关层，常用算法的物理特性有着严格分工：

  • 固定窗口计数器：最粗糙，存在跨窗口临界爆发（前一秒后半段与后一秒前半段瞬间涌入 2 倍限额）。
  • 滑动窗口日志 / 计数器：通过平滑统计最近 60s 内的请求加权和，消灭临界突刺，但内存占用略高。
  • 漏桶算法 (Leaky Bucket)：以绝对恒定速率流出，常用于对下游写数据库限速，完全禁止突发。
  • 令牌桶算法 (Token Bucket)：允许突发流量消费预存令牌，适合面向用户的 API 网关。

高吞吐消息引擎与流处理语义 (Kafka Partitions & Exactly-Once Semantics - EOS)

Zero-Copy · 事务日志

Kafka 单机数十万 QPS 的底层架构密码在于绕过 JVM 垃圾回收与消灭内存拷贝：

// Kafka 物理吞吐优化核心三板斧：
1. 顺序写磁盘 (Sequential Append): 机械硬盘顺序写性能接近内存随机写，避免磁头反复寻道。
2. PageCache 与 Zero-Copy: 使用 Linux sendfile(in_fd, out_fd) 系统调用，网卡直接从 OS PageCache 读取数据包，零上下文切换。
3. 端到端 EOS: 生产者分配 PID + Sequence Number 解决幂等，结合 beginTransaction() / commitTransaction() 确保消费位移与下游产出原子提交。
POINT 09

服务高可用弹性与防雪崩模式：断路器、全抖动重试与过载脱离

Full Jitter · 自适应负载保护
// ASD-STE100 架构规约：

1. Blind retries create a Retry Storm that crashes recovering backends.

2. Exponential backoff increases delay between retries exponentially: \(t = b \times 2^i\).

3. Full Jitter chooses a random sleep time uniformly between 0 and \(t\), breaking synchronization spikes.

4. Load Shedding drops low-priority requests based on queue latency before CPU reaches 100% saturation.

POINT 10

分布式全局唯一 ID 生成体系与时钟回拨处理 (Snowflake & NTP Skew)

64 位位运算 · 美团 Leaf 思想

Twitter Snowflake 64 位整型 ID 保证趋势递增（对 B+ Tree 聚簇索引极其友好），但强依赖物理时钟单调递增：

// Snowflake 64-bit 结构剖析：
[0] 1位符号位 (恒为0)
[1..41] 41位时间戳 (支持 69 年)
[42..51] 10位工作机器 ID (支持 1024 个节点)
[52..63] 12位毫秒内自增序列 (支持单机 4096 QPS/ms)

时钟回拨解决方案：微小回拨（<5ms）采用自旋等待；中度回拨（5~2000ms）切换备用 WorkerID 逻辑槽位；重度回拨报警人工介入；美团 Leaf 双 Buffer 架构预先从 DB 取号段，彻底脱钩时钟。

POINT 11

无主复制与 Quorum 读写仲裁机制 (Dynamo Quorum & Anti-Entropy)

R + W > N · 向量时钟
// ASD-STE100 架构规约：

1. In leaderless replication, any node accepts writes and reads.

2. Set total replicas \(N\), write quorum \(W\), and read quorum \(R\).

3. If \(R + W > N\), the read set and write set must overlap by at least one node.

4. This guarantees that reads always discover the newest written value version.
